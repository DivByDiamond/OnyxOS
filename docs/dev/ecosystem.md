# Ecosystem: зависимости между репозиториями Onyx

Проектный документ. Здесь описана текущая структура семи
репозиториев и собраны варианты её улучшения. Предложения 1, 4 и 5
исполнены 2026-11-21 (см. статусные строки в их секциях); остальные
ждут решения владельца.

## Граф зависимостей

Сборку всегда ведёт OnyxOS. Он подтягивает остальные репозитории как
соседние чекауты в `.vent/repos/` по `Onyx.vent` (URL) и `Onyx.lock.json`
(точные ревизии), затем собирает их в порядке зависимостей и собирает
итоговые образы.

```
                 OnyxOS (оркестратор)
                     |
        .vent/repos/ (залоченные чекауты, Onyx.vent + Onyx.lock.json)
                     |
   +--------+--------+---------+------------------+---------+
   |        |        |         |                  |         |
OnyxBoot OnyxKernel OnyxShell OnyxCompiller   OnyxApps  OnyxDesktop

Цепочка сборки образа:

OnyxBoot -> OnyxKernel -> init -> OnyxShell -> OnyxCompiller
                                              |
                                   OnyxApps / OnyxDesktop (собираются onyxcc)
                                              |
                                   образ диска (FAT32 + OnyxFS) и flash-образ OC2R
```

ABI это контракт между четырьмя репозиториями: ядро объявляет системные
вызовы, шелл и компилятор зависят от их сигнатур и структур. Согласованность
проверяет `scripts/check-abi.sh`: он вызывает
`OnyxKernel/scripts/generate-syscalls.py --check` с каталогами OnyxShell и
OnyxCompiller. `scripts/build-all.sh` запускает эту проверку автоматически.
Половинчатое изменение ABI ломает загрузку, поэтому правки ядра, init,
шелла и компилятора делаются синхронно во всех затронутых репозиториях.

## Роль каждого репозитория

- **OnyxOS**: оркестратор экосистемы. Зависимости (`Onyx.vent`,
  `Onyx.lock.json`), сборка всех компонентов, образ диска FAT32 + OnyxFS,
  flash-образ OC2R, скрипты QEMU, интеграционные дымовые тесты, общая
  документация (`docs/dev`, `docs/internals`, `docs/hardware`).
- **OnyxKernel**: монолитное ядро RISC-V 64 (Sv39, три кольца привилегий).
  Содержит общий код `onyx_core`, userspace `init`, host-инструменты
  (`mkimage`, `elf2onx`, `psfgen`). Объявляет ABI системных вызовов.
- **OnyxBoot**: загрузчик M-mode на C++20. UART/FDT, VirtIO, SDHCI,
  FAT32/ext4, ELF64. Загружает ядро в QEMU и на железе; в dev-режиме QEMU
  может грузить ядро напрямую, минуя его.
- **OnyxShell**: шелл `osh` на Rust (freestanding). Единственный
  пользовательский интерфейс системы; ABI-потребитель ядра.
- **OnyxCompiller**: самохостинг-компилятор C99 `onyxcc` и линкер
  `onyx-ld`. Собирает пользовательские приложения; ABI-потребитель ядра.
- **OnyxApps**: пользовательские приложения на C99, собираются
  OnyxCompiller в формат `.onx`.
- **OnyxDesktop**: окружение рабочего стола `onyxdesk` на C99, поверх того
  же ABI и инструментов сборки, что и OnyxApps.

## Возможные улучшения

Варианты, не исполнены. У каждого свои плюсы и минусы.

### 1. Единый интерфейс сборки компонентов

Сейчас у каждого репозитория своя команда входа: `make` (OnyxBoot,
OnyxCompiller), `cargo kbuild` (OnyxKernel), `bash build.sh` (OnyxShell).
Можно ввести одинаковый интерфейс, например `make build` и `make test` в
корне каждого репозитория.

Плюсы: одна команда для всех компонентов, проще скрипты оркестратора и
CI, меньше ошибок от рассинхронизации документации.
Минусы: дублирование логики в семи Makefile, риск сломать привычные
команды у существующих пользователей, нужна синхронная правка всех
репозиториев.

### 2. VERSION-файл для синхронизации версий

Версия прошивки в `oc2r-firmware.json`, версия workspace `Cargo.toml`
OnyxKernel и номер релиза в roadmap сейчас согласуются вручную. Можно
завести один файл версии в OnyxOS и подставлять его в манифест и шилдсы
автоматически.

Плюсы: версия в README, манифесте и релизах перестаёт расходиться,
бейджи всех репозиториев обновляются из одного места.
Минусы: генерация файлов при сборке усложняет CI, у компонентов остаются
свои внутренние версии, которые не обязаны совпадать с версией экосистемы.

### 3. Дедупликация документации между репозиториями

Темы пересекаются: порядок блокировок и ABI описаны и в OnyxKernel, и в
доках OnyxOS; стилевые спеки README теперь лежат в каждом репо. Можно
свести общие темы в один документ в OnyxOS и ссылаться на него из
остальных репозиториев.

Плюсы: одна точка правды для ABI и сборки, меньше расползающихся копий.
Минусы: ссылка на внешний репозиторий вместо локального файла, при
клонировании одного компонента часть документации недоступна, лок
ревизий требует отдельной дисциплины при обновлении общего документа.

### 4. Скрипт проверки таблицы экосистемы

Таблица экосистемы должна быть дословно одинаковой во всех семи README.
Сейчас это контролируется вручную. Можно добавить скрипт, который берёт
эталонную таблицу из спеки стиля и сверяет её со всеми README.

Плюсы: расхождение ловится в CI автоматически, рефакторинг таблицы
перестаёт быть ручной работой по семи файлам.
Минусы: ещё один служебный скрипт ради одной таблицы, надо решить, где
живёт эталон и кто его обновляет.

Сделано 2026-11-21: scripts/check-ecosystem-table.py

### 5. Судьба build.sh и build-ultra.sh в корне OnyxOS

В корне репозитория лежат `build.sh` и `build-ultra.sh`, которые правят
профили Cargo.toml соседних чекаутов (opt-level, debug, strip) и собирают
ядро, init и шелл напрямую. Их область покрыта `scripts/build-all.sh` с
залоченными ревизиями и `ONYX_DEPS_MODE=workspace` для локальных
деревьев. Варианты: удалить оба, оставить как «тонкую» сборку для
быстрого цикла разработки или перенести в `scripts/` с описанием в
`docs/dev/building.md`.

Плюсы удаления: один путь сборки вместо трёх, меньше мест, где sed правит
чужие Cargo.toml, меньше сюрпризов с профилями.
Минусы: потеря быстрого цикла пересборки ядра и шелла без полного
пайплайна; любому, кто ими пользуется, придётся перейти на workspace-режим
`build-all.sh`.

Сделано 2026-11-21: оба скрипта удалены, быстрый цикл описан в
`docs/dev/building.md`.
